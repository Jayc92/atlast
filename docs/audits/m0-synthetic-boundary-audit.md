## 11. Residual Limitations of Static Scanning

This audit is a point-in-time static review and cannot prove:

- **Absence of every possible secret.** Pattern scans catch known credential formats and naming conventions; a novel or obfuscated secret format could evade them. Mitigation: small reviewed surface, `.gitignore` exclusions, and human review of every change ([GUARDRAILS.md § 3.3](../../GUARDRAILS.md#33-pull-requests)).
- **Third-party dependency behavior.** Declared dependencies were audited by capability surface, not by reading their implementations. Supply-chain behavior (e.g., a compromised package making network calls) is outside static first-party review. Mitigation: exact version pins, frozen-lockfile installs, minimal dependency count.
- **Future changes.** This audit binds only commit `4111d24`. Any change adding dependencies, network code, environment access, or fixture data moves the boundary and warrants re-audit — in particular at M1 (fixture data) and M5 (first real connector).
- **Git history.** The audit examined the tracked tree at HEAD, not every historical blob. The repository is young and has been committed directly to `main` through explicit human review checkpoints — the current tree was reviewed at those checkpoints, but the full Git history was not independently secret-scanned.

**NUL-byte / binary-classification sweep (new in this re-audit, corrected mid-review, then resolved) — Result: one finding, found and then remediated within this candidate.** The first pass of this check used `grep -P '\x00'` per tracked file and reported none found. That method was unsound: it does not put a literal NUL in a shell argument (the pattern is the four-character string `\`, `x`, `0`, `0`, interpreted internally by the regex engine — the concern the task instruction raised does not apply to it), but it silently failed to match an actual embedded NUL byte in at least one real file, for a reason not further diagnosed here. The check was rerun with a byte-safe method that reads every one of the 180 git-tracked files as raw bytes in Python (`open(path, "rb").read()`, then `b"\x00" in data`) rather than shelling out per file.

**Finding (as first discovered):** `packages/graph-model/src/reconciliation.ts` (merged Slice S5, PR #19, `0923e9c`) contained exactly one embedded NUL byte, at byte offset 8298 of 21838, inside the `draftKey` composite-key builder — a delimiter between two interpolated segments, the same purpose and the same defect class as the NUL byte the S6 independent review found and fixed in `snapshot-resolver.ts`'s `identityCacheKey` before that PR merged (recorded in [TASKS.md](../../TASKS.md)'s S6 entry).

**Binary-classification cross-check (corrected wording):** the byte-safe scan is what actually found the literal NUL — Git's own tooling did not surface it. Independently, `git grep -Iz -l ''` (Git's own text/binary heuristic) still listed the file, and `git log --numstat` reported ordinary text line counts (616 added, 0 removed) for its introducing commit — both treated the introducing change as text, not as binary. Running `git show HEAD:<path> | file -` against the pre-fix blob returned the generic classification `data`; **that result is inconclusive, not proof of non-binary content** — `file`'s `data` label means only that its heuristics did not match a more specific known type, and it must not be cited as having confirmed the file was text. The accurate statement is: Git's own diff/grep/log tooling treated the pre-fix file as text (so it was not invisible to `git diff`/`git grep`/`git log`, unlike the S6 `snapshot-resolver.ts` case), while the external `file` command's result on the same blob was inconclusive either way.
