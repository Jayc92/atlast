# Architecture Decision Records

Binding decisions are made only through human-approved ADRs ([GUARDRAILS.md § 1.3](../../GUARDRAILS.md#13-change-discipline)). Format: `NNNN-short-title.md` with Context, Problem, Decision, Alternatives Considered, Tradeoffs, Consequences, Risks, fit rationale, and change conditions. Statuses: **Proposed → Accepted → Superseded** (or **Rejected**).

### ADR-0024 pre-acceptance review and correction record (historical)

Preserved as the record of the review and correction cycle that preceded the acceptance above; nothing below reflects ADR-0024's current (Accepted) status — the approval note above states that.

**Review note (2026-08-11, ADR-0024):** ADR-0024 is the output of the S7 pre-release architecture and contract review (requested per [CLAUDE.md](../../CLAUDE.md) and [HANDOFF.md § 7](../../HANDOFF.md)), performed after S6's formal closure (PR #24). It audits eighteen assigned S7-readiness review points against accepted ADR-0017 (as amended by ADR-0020) and the merged S2/S6 contracts, finds seven already fully specified, and proposes settling fifteen genuine, implementation-critical gaps. **An independent correction pass, applied the same review cycle, closed several items the first draft had deferred rather than settled**: an exact per-route parameter matrix; the exact snapshot-summary HTTP envelope (resolving the mismatch between ADR-0017's general envelope and the repository's flat `SnapshotSummary`); a single closed, discriminated error-response union with an exact `details` shape and status per code (replacing an open-ended `code: z.string()`/`details: z.unknown()`), including previously unmapped Fastify route-not-found and unexpected-exception cases and an explicit redaction policy; a corrected, factually accurate statement of Fastify's repeated-query-key behavior (withdrawing an incorrect claim naming `qs` as the parser); an explicit asynchronous application-initialization lifecycle guaranteeing no request can be served before fixture ingestion completes; a corrected direct-dependency decision (`apps/api` depends directly on both `@atlast/graph-model` and `@atlast/shared`, not one transitively through the other); and — following an audit of the actual current package manifests and tsconfigs — a confirmed, production-valid package-entry-point build strategy for `packages/shared` and `packages/graph-model`, since neither currently produces build output or declares an entry point, and the existing test-only source-alias convention alone cannot make a compiled `apps/api` resolve them at runtime. The review also found that accepted ADR-0020's phrase "entity detail and traversal" is factually imprecise (entity detail can never return a Relationship subject) and would require its own metadata-only amendment, in addition to ADR-0017's.

**Second review note (2026-08-11, ADR-0024, third-pass correction):** a further independent correction pass, made after reading the actual current `tsconfig.json`/`tsconfig.build.json` files and the S6 cursor implementation directly, found the prior revision had asserted, rather than proven, that its build strategy would work, and had left three further specifics incorrect or unenforceable. ADR-0024 was revised again (still **Status: Proposed**) to: (1) complete the `packages/shared`/`packages/graph-model` build configuration with `declaration: true` output and an explicit empty `paths` override during emit builds (an inherited source-alias `paths` mapping left active during a build can pull a dependency's source outside the consuming package's `rootDir`, corrupting the package boundary), extend the same override to `apps/api/tsconfig.build.json`, and require an explicit clean-build-then-run proof (`rm -rf` each package's `dist/`, `pnpm build`, `node apps/api/dist/server.js`) rather than declaring the strategy correct "by construction"; (2) remove a proposed health-only `buildApplication` mode that would have produced two different application shapes, conflicting with ADR-0009's fully-assembled-application testing requirement — `buildApplication` now always requires its full repository dependencies, and the existing `app.test.ts` is explicitly scoped as an S7 change (no longer claimed to remain byte-for-byte unchanged); (3) correct the cursor-transport policy, withdrawing an unenforceable invariant (that a cursor's _originating_ latest-or-pinned request mode could be checked) the S6 cursor payload does not encode, replacing it with the two behaviors the repository actually implements and an explicit statement that transport-mode history is not cursor-bound and is not inferred; and (4) tighten the closed error-response schema so `mismatchFields`, horizon/watermark, and derivation-version fields reuse the repository's own existing bounded schemas instead of permissive `z.string()`/`z.number()`, so `CURSOR_BINDING_MISMATCH`'s graph and evidence variants stay the two exact, disjoint shapes the repository error already defines rather than one shape with every field optional, and so the `MALFORMED_REQUEST` claim is narrowed to failures Fastify's own `setErrorHandler` actually governs, not raw Node-level HTTP parser failures. The seven-route surface (§ 1) is unchanged by this pass. **No accepted ADR was edited.** **This document remains Proposed, not Accepted, and none of its three drafts authorizes M1 Slice S7 implementation** — S7 remains gated pending its own separate, explicit human release recorded in [TASKS.md](../../TASKS.md), exactly as [HANDOFF.md](../../HANDOFF.md) and [docs/milestones.md](../milestones.md) require.

**Third review note (2026-08-11, ADR-0024, fourth-pass correction):** a further, narrowly scoped correction found that the third pass's own proposed `packages/shared/tsconfig.build.json` and `packages/graph-model/tsconfig.build.json` still fail to build: both packages combine `"allowImportingTsExtensions": true` with relative `.ts`-extensioned imports in their existing `tsconfig.json`, satisfied today only because that base config is `noEmit: true`; a build config that sets `noEmit: false` without also setting `rewriteRelativeImportExtensions` (or `emitDeclarationOnly`) satisfies none of `allowImportingTsExtensions`'s three permitted conditions, and `tsc` rejects it outright with TS5096. ADR-0024 § 14 was revised again (still **Status: Proposed**; the resolved-gap count stays at fifteen — this pass narrows § 14 further rather than adding a gap) to add `"rewriteRelativeImportExtensions": true` to both packages' `tsconfig.build.json` files only — never to either package's existing no-emit `tsconfig.json` — which simultaneously satisfies `allowImportingTsExtensions`'s constraint during emit and rewrites each package's relative `.ts` import specifiers to `.js` in the emitted output. `apps/api/tsconfig.build.json` needs no equivalent addition: `apps/api/tsconfig.json` already sets `rewriteRelativeImportExtensions: true` directly (it never uses `allowImportingTsExtensions`), so its build config already inherits the setting. The Exact S7 Boundary, build-strategy narrative, and testable invariants (§ 14) were updated to reflect this. **No accepted ADR was edited.** **This document remains Proposed, not Accepted, and none of its four drafts authorizes M1 Slice S7 implementation** — S7 remains gated pending its own separate, explicit human release recorded in [TASKS.md](../../TASKS.md), exactly as [HANDOFF.md](../../HANDOFF.md) and [docs/milestones.md](../milestones.md) require.
