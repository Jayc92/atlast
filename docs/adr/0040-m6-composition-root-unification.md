# ADR-0040: M6 Browser-Facing Composition-Root Unification

**Status:** Accepted
**Date:** 2026-08-24 (revised 2026-08-24 after independent adversarial review; accepted 2026-08-24 as part of the complete M6 baseline — see acceptance note)

> **Acceptance note (2026-08-24):** Joseph Carfagno explicitly accepted this ADR on 2026-08-24 as part of the complete M6 baseline ([docs/m6-plan.md](../m6-plan.md)), after both an adversarial review and a genuinely independent final review found no substantive blocker. **Acceptance authorizes no implementation.** The first M6 implementation slice referencing this ADR (M6-A, per [docs/m6-plan.md § 20](../m6-plan.md#20-proposed-implementation-slices-shapes-only--none-authorized)) requires its own separate, explicit human authorization, effective only after this acceptance record merges to `main` and local `main` synchronizes cleanly.

> **Revision note (adversarial review pass):** the first draft correctly identified the composition-root split as the primary blocker and correctly rejected mixing synthetic and connector data in one store, but left two things underspecified: (1) it never named the full set of dataset-mode alternatives or stated why a _visible_ mode indicator matters, beyond "one store"; (2) it said nothing about the connector's operational lifecycle (pre-flight failure, mid-session source loss, shutdown, double-start risk) — the exact set of real failure modes a pilot will actually hit. Both are addressed below (§§ 1, 6).

## Context

[docs/m5-plan.md § 6](../m5-plan.md#6-deferred-m5-slices) explicitly left open, and never decided, "whether the M5-A experiment composition root should ever be unified with the normal application composition root — or remain permanently separate." M6's product-testability reconnaissance (2026-08-24, this session) settled the factual question that open question depended on: direct inspection of the merged `main` codebase confirms `apps/api/src/server.ts` (the production entrypoint `apps/web`'s Vite proxy is hardcoded to, at `127.0.0.1:3001`) and `apps/api/src/server-m5-kubernetes-experiment.ts` (M5-A's experiment entrypoint, port 3901) each call `apps/api/src/app.ts`'s `initializeStores` independently — "each call constructs its own fresh pair; there is no shared singleton," per that function's own doc comment. `packages/connectors/src/kubernetes/**` is imported only by the experiment entrypoint; nothing in the production path imports `@atlast/connectors` at all. **Today, running the Kubernetes connector and starting the normal Atlast website produces zero visible effect in the browser** — this is the concrete blocker the M6 employee-validation journey ([docs/m6-plan.md § 6](../m6-plan.md#6-target-employee-journey)) cannot proceed past without a decision.

## Problem

Decide how real, connector-derived Evidence reaches the same `EvidenceStore`/`TopologyGraphStore` the normal, browser-facing Atlast API and web application read from — without creating two competing product stores, without weakening ADR-0009's "one application shape" invariant, and without regressing the existing, fully-synthetic M0–M5 capability that must remain selectable and intact. A correct answer must also let the tester unambiguously know which dataset they are looking at, and must define what happens when the Kubernetes connector fails before, or fails during, a pilot session — not merely how data reaches the store on the happy path.

## Decision

### 1. Dataset mode: connector-only, mutually exclusive with fixtures, with a visible mode indicator

Four dataset-composition alternatives were evaluated:

| Option                                                                                                                                                                                  | Shape                                                                                                                                                                                                                                                                                                   | Verdict                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A. Simultaneous** — fixture-seeded and connector-seeded Evidence in one store at once.                                                                                                | Mixes real and synthetic Evidence in one store.                                                                                                                                                                                                                                                         | **Rejected.** Exactly what M5-A's own design deliberately avoided ("this experiment never mixes real Kubernetes-sourced Evidence with the `demo-company` fixture catalog in one store," `docs/m5-plan.md § 6`); would contaminate the pilot scorecard with entities the tester never expects to see, and reopens the `recordedSequence` ownership question `initializeStores`/`EvidenceStore.appendEvidence` require a single strictly-increasing owner for. |
| **B. Connector-only pilot mode** — the running process is seeded from exactly one source (fixtures, the existing default; or the connector, this ADR's new opt-in path) and never both. | One store, one dataset, chosen at process start.                                                                                                                                                                                                                                                        | **Chosen**, combined with § 1's visibility requirement below.                                                                                                                                                                                                                                                                                                                                                                                                |
| **C. Explicit runtime-selected, multi-dataset mode** (e.g. a request-time or session-time switch between fixture and connector views).                                                  | Would require either two live stores behind one process (reintroducing the "two competing product stores" problem this ADR exists to close) or dynamically re-seeding one store per request (breaking the append-only, monotonic-horizon invariant every existing snapshot/cursor mechanism relies on). | **Rejected**: not the smallest correct model, and in tension with "one running product instance should have one authoritative store graph."                                                                                                                                                                                                                                                                                                                  |
| **D. A different process per dataset, `apps/web` configured to choose.**                                                                                                                | Requires new `apps/web` configuration/UI to select a backend, which the reconnaissance found no other reason to add.                                                                                                                                                                                    | **Rejected**: reintroduces exactly the "teach `apps/web` about two backends" alternative already rejected below (§ Alternatives Considered).                                                                                                                                                                                                                                                                                                                 |

**Option B is chosen**, with one addition the first draft omitted: the running process's active dataset mode MUST be **visibly, authoritatively knowable** — not merely inferable from which entities happen to appear. Concretely, the existing `/health` response (or an equivalent, minimally invasive addition) is extended to report which mode the process is running in (e.g. `"dataset": "synthetic-fixtures"` vs. `"dataset": "kubernetes-connector"`). This directly serves two requirements at once: it lets the tester (and the § 9 visual-source-badge UI work) confirm unambiguously which topology they are evaluating, and it gives the pilot-feedback artifact (ADR-0041) a durable, authoritative fact to record in its session metadata, rather than relying on the tester's own assumption about which mode they started.

### 2. One production entrypoint, connector-aware by configuration

`apps/api/src/server.ts` (or its direct successor under this ADR) becomes the **single** production/pilot entrypoint. It gains an explicit, opt-in configuration path (naming TBD at implementation — an environment variable or CLI flag, not a default-on behavior) that, when present, seeds the store from the Kubernetes connector instead of the `demo-company` fixtures, and additionally starts the connector's poll loop against the _same_ `EvidenceStore` instance the application is already serving reads from — reusing the exact seam `initializeApplicationExposingStores` already proved works for M5-A (`dependencies.evidenceStore.appendEvidence(...)` against the running application's own store).

When that configuration path is absent, the entrypoint behaves **exactly** as it does today: fixture-seeded, no connector, no Kubernetes dependency loaded — existing M0–M5 synthetic capability is unaffected and remains the default.

### 3. `apps/web` requires no change

Because `apps/web/vite.config.ts`'s proxy target is already hardcoded to whichever process is bound to `127.0.0.1:3001`, and this ADR keeps that the one production port, **no `apps/web` code change is required** for data to flow through — the browser automatically sees connector-derived entities the moment they exist in the store the already-running production process serves reads from, exactly as it already does for fixture data today. (§ 1's `/health` mode field is a small, additive `apps/web` consumption point for the § 9 visual-badge work, not a proxy/routing change.)

### 4. `apps/api/src/server-m5-kubernetes-experiment.ts`'s disposition

The existing M5-A experiment entrypoint MAY remain in the repository as historical/test tooling — it is real, merged, working code with its own durable evidence record ([docs/audits/m0-synthetic-boundary-audit.md § 21](../audits/m0-synthetic-boundary-audit.md)) — but it MUST NOT be the pilot's product path, and no M6 acceptance evidence may be gathered against it. Whether to delete it, keep it as-is, or fold its remaining unique value into documentation only is an implementation-time decision this ADR does not need to make now.

### 5. `ApplicationDependencies`/`initializeApplication` shape is unaffected

`apps/api/src/app.ts`'s `buildApplication`, `ApplicationDependencies`, and the underlying `InMemoryEvidenceStore`/`InMemoryTopologyGraphStore` pair are **not modified** by this decision. The unification happens entirely at the composition-root/entrypoint layer — exactly the layer `initializeApplicationExposingStores` already demonstrated can vary without touching `buildApplication`'s registered route/schema/query behavior, preserving ADR-0009's "one application shape" invariant. `EvidenceStore.appendEvidence`'s strictly-increasing `recordedSequence` requirement is satisfied trivially by § 1's mutual-exclusivity rule: exactly one sequence owner (fixture-seeding or the connector) is ever active in a given process.

### 6. Connector operational lifecycle (new — the first draft did not address this)

| Situation                                                                                                                                                                          | Required behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pre-flight failure** (target guard or RBAC check fails before any discovery starts — [ADR-0042-successor content, docs/m6-plan.md § 8](../m6-plan.md#8-connectscan-experience)). | The entrypoint MUST exit fatally **before** binding its listening port — mirroring the existing `startServer().catch(...)`/`startExperiment().catch(...)` fatal-startup pattern already in this codebase. It must never start serving in a state where discovery silently never happened.                                                                                                                                                                             |
| **Kubernetes becomes unavailable after the application is already listening and serving requests** (mid-session source loss).                                                      | **No new design needed.** This is exactly the situation M5's own source-loss/freshness proof (`docs/audits/m0-synthetic-boundary-audit.md § 22`) already exercised and proved correct: poll failures are logged (the existing `pollOnce().catch(...)` pattern), the process stays alive and keeps serving, and reads honestly reflect the frozen/aging Evidence via the existing pinned-`asOf` freshness contract. This ADR carries that behavior forward unmodified. |
| **Shutdown** (`SIGINT`/`SIGTERM`).                                                                                                                                                 | The existing handling in both current entrypoints (stop the poll timer, close the Fastify instance, exit) already does this correctly and must be preserved in the unified entrypoint.                                                                                                                                                                                                                                                                                |
| **Two stores/processes accidentally created simultaneously** (e.g. someone starts both a fixture-mode and a connector-mode process).                                               | Structurally prevented, not by new code: both modes bind to the same one production port by design (§ 3); the OS's own port-exclusivity (`EADDRINUSE`) makes a second simultaneous bind fail loudly. No new safeguard is required beyond keeping both modes on the same port.                                                                                                                                                                                         |

## Contractual Invariants This Unification Must Preserve

- ADR-0009's "the fully assembled application... one application shape, never two" — `buildApplication` remains called identically regardless of which composition path invokes it.
- No existing route, schema, or query behavior changes for any caller, fixture-seeded or connector-seeded.
- Existing M0–M5 synthetic capability remains fully intact and is the unmodified default when the new opt-in path is absent.
- `apps/web` remains unaware of which mode the backend is running in for its core query behavior — it reads the same query API either way, exactly as [ADR-0026](0026-m2-browser-architecture-and-api-boundary.md)'s query-only client boundary already requires; the § 1 mode field is additive metadata, not a behavior branch in the client's query logic.
- Fixture-seeding and connector-seeding are never simultaneously active in one process (§ 1/§ 5) — this closes the `recordedSequence`-ownership question the first draft deferred rather than left genuinely open.

## Alternatives Considered

- **Keep the two entrypoints permanently separate; teach `apps/web` to point at whichever port the tester's backend happens to use.** Rejected: exactly the "second, competing product path" this ADR's Problem statement forbids, and would require `apps/web` configuration/UI changes the reconnaissance found no other reason to make; also risks normalizing a permanently bifurcated product, contrary to [docs/m5-plan.md § 6](../m5-plan.md#6-deferred-m5-slices)'s framing of the M5-A split as "a deliberate, temporary experimental seam... not a permanent architectural decision."
- **Merge fixture-seeding and connector-seeding into one store simultaneously ("hybrid mode") — Option A above.** Rejected for the reasons in § 1's table.
- **Build a third, new entrypoint specifically for the pilot, distinct from both existing ones.** Rejected: reintroduces the exact "two competing product stores" problem this ADR exists to close, just with a third file instead of a second.
- **Say nothing about connector failure modes and leave it to implementation.** Rejected on adversarial review: the M5 source-loss proof already establishes the correct mid-session behavior; failing to name it here risks a future implementer re-deriving (or getting wrong) behavior this project has already proven once.

## Tradeoffs

- **Chosen:** one production entrypoint with an opt-in, mutually-exclusive, visibly-reported connector mode, requiring zero `apps/web` query-behavior change and preserving ADR-0009's invariant exactly — at the cost of a real, if bounded, `apps/api/src/server.ts` (or successor) change that must be implemented and reviewed carefully to avoid regressing the fixture-only default path.
- **Given up:** the M5-A pattern's simplicity of "a completely separate process nothing else can affect," in exchange for actually satisfying the M6 product hypothesis, which the separate-process pattern structurally cannot.

## Consequences

- `apps/api/src/server.ts` (or its direct successor) gains real complexity: a configuration-driven choice between fixture-seeding and connector-seeding, plus a reported mode field, where today it does exactly one thing unconditionally.
- `apps/api` gains its first production-path dependency on `@atlast/connectors` — a boundary that did not exist before M6, and that the existing synthetic-boundary audit convention should re-scan once this lands, naming exactly this new dependency edge.
- The M5-A experiment entrypoint's ongoing role (§ 4) is an open implementation-time question this ADR deliberately leaves unresolved rather than deciding prematurely.
- The connector lifecycle table (§ 6) becomes a concrete implementation and test checklist, not merely a design aspiration.

## Risks

- **Regressing the default fixture-only path while adding the opt-in connector path.** Mitigation: the complete existing `apps/api`/`apps/web`/browser-acceptance test suites must pass unchanged with the new configuration path absent.
- **Accidentally making the connector path the default, or reachable without explicit opt-in.** Mitigation: implementation review must verify the opt-in configuration is off by default and requires an explicit, positive action to enable.
- **The `/health` mode field being treated as authenticatable/sensitive when it is not.** Mitigation: the field reports only which synthetic-vs-real dataset is active, never credential or cluster-identifying detail — consistent with `/health`'s existing, unauthenticated, low-sensitivity contract.

## Why This Fits Atlast

- **E4 — Boring reliability** ([PROJECT_SPEC.md § 2.2](../../PROJECT_SPEC.md#22-engineering-goals)): one entrypoint with a configuration switch, and a proven, unmodified source-loss behavior, is simpler and more reliable than two permanently diverging processes with undefined failure behavior.
- **ADR-0009's "one application shape" invariant** is preserved exactly, not weakened, by keeping the unification at the composition-root layer only.
- **Fail honest** ([PROJECT_SPEC.md Principle 8](../../PROJECT_SPEC.md#3-guiding-principles)): the visible mode indicator (§ 1) is a direct implementation of "the employee must unambiguously know which topology they are evaluating."

## Conditions That Would Justify Changing This Decision

- Implementation review finds the opt-in configuration cannot be added to `server.ts` without materially complicating its existing, simple startup-failure and shutdown handling — in which case a cleaner split (e.g., a thin wrapper entrypoint that itself calls the unified composition function) may be the better implementation, without changing this ADR's underlying decision that there is exactly one production store the browser reads from.
- A future milestone needs the fixture-seeded and connector-seeded paths to run simultaneously in one process — not needed by M6 and not authorized here; would require its own ADR addressing the sequence-number and provenance-mixing questions § 1's Option A rejection explicitly defers.

This Accepted ADR does not itself authorize implementation. The first M6 implementation slice referencing it requires its own separate, explicit human authorization, effective only after this acceptance record merges to `main` with local `main` synchronized cleanly.
