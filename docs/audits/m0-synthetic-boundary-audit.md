## 11. Residual Limitations of Static Scanning

This audit is a point-in-time static review and cannot prove:

- **Absence of every possible secret.** Pattern scans catch known credential formats and naming conventions; a novel or obfuscated secret format could evade them. Mitigation: small reviewed surface, `.gitignore` exclusions, and human review of every change ([GUARDRAILS.md § 3.3](../../GUARDRAILS.md#33-pull-requests)).
- **Third-party dependency behavior.** Declared dependencies were audited by capability surface, not by reading their implementations. Supply-chain behavior (e.g., a compromised package making network calls) is outside static first-party review. Mitigation: exact version pins, frozen-lockfile installs, minimal dependency count.
- **Future changes.** This audit binds only commit `4111d24`. Any change adding dependencies, network code, environment access, or fixture data moves the boundary and warrants re-audit — in particular at M1 (fixture data) and M5 (first real connector).
- **Git history.** The audit examined the tracked tree at HEAD, not every historical blob. The repository is young and has been committed directly to `main` through explicit human review checkpoints — the current tree was reviewed at those checkpoints, but the full Git history was not independently secret-scanned.

### 21.7 Identity Case Study — A Real Finding, Not a Clean Mapping

**Initial real mapping attempt:** `sourceScopedIdentity.sourceNativeId = "atlast-m5/atlast-m5-live-pod"` (slash-joined namespace/name, the natural Kubernetes convention).

**Result: rejected.** Running this through the real, unmodified `m1-v1` engine (`packages/graph-model/src/identity-normalization.ts`'s `normalizeIdentityKey`, ADR-0022 § 2) threw `IdentityNormalizationError`. The accepted identity grammar (`LOWERCASE_ASCII_KEY_PATTERN`) is exactly:

```
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

— lowercase alphanumeric segments joined only by single hyphens. A literal `/` is outside this grammar and is rejected outright, loudly, exactly as ADR-0022 § 2 specifies.

**The connector was changed — not the identity algorithm.** No line of `packages/graph-model` or any accepted ADR was modified. The connector's own `sourceNativeId` construction (`packages/connectors/src/kubernetes/evidence-mapping.ts`) was changed to hyphen-join instead: `"atlast-m5-atlast-m5-live-pod"`.

**Final result, this one observed Pod:**

- Canonical entity: `atlast:entity:atlast-m5-atlast-m5-live-pod`
- Confidence: `0.5`
- Rule: `normalized-exact-match`
- Ambiguity/conflict: none, for this single observed Pod.

**This does not universally solve Kubernetes identity, and is not presented as doing so.** Hyphen-joining namespace and name introduces its own **potential collision**, recorded here explicitly as a factual M5 finding requiring consideration before Kubernetes identity coverage broadens beyond this first Pod-only experiment: namespace/name combinations can theoretically collapse to the same hyphen-joined string if the component boundary differs. For example, a Pod named `live-pod` in namespace `atlast-m5` (`"atlast-m5" + "-" + "live-pod"` → `"atlast-m5-live-pod"`) would normalize to the _same_ key as a Pod named `m5-live-pod` in a namespace named `atlast` (`"atlast" + "-" + "m5-live-pod"` → `"atlast-m5-live-pod"`) — two genuinely distinct real Kubernetes objects, indistinguishable after this hyphen-join. This experiment's own single real Pod did not exhibit this collision, and no redesign of identity resolution is proposed or performed in this checkpoint — the finding is recorded so it is weighed deliberately, not discovered by accident, before any later M5 slice widens Kubernetes resource or namespace coverage.

## 23. ADR-0018 Real-M5-Workload Storage Reassessment (2026-08-21)

### 23.1 Observed M5 Cardinality

### 23.2 Measurement Methodology

A temporary, non-repository Node script (`/tmp/atlast-adr0018-measurement.mjs`, written, run, and deleted within this same session — the identical ad-hoc-measurement convention § 20.7 already used for the browser-memory figure; confirmed absent via `git status --short` before and after) exercised the **exact, unmodified production read/freshness path**: `InMemoryTopologyGraphStore.getSubject` (the same method `GET /api/v1/entities/{entityId}` composes) → `SnapshotResolver` → `reconcileEvidenceAtHorizon` → `buildAssertionReadResult` → `latestSupportingObservedAt`'s per-provenance `EvidenceStore.getEvidenceByIdentifier` loop.

No Kubernetes, no network, and no new dependency were involved; no production file was modified.

**Environment:** Node.js `v24.15.0`, `arm64`, `darwin` (same machine and Node version as every other measurement in this document).

### 23.3 Latency Results

| Cardinality | Samples | Median      | p95          | Min         | Max          |
| ----------- | ------- | ----------- | ------------ | ----------- | ------------ |
| 20          | 30      | 1.57 ms     | 2.70 ms      | 1.06 ms     | 4.27 ms      |
| 1,000       | 30      | 670.13 ms   | 709.40 ms    | 656.55 ms   | 731.49 ms    |

The growth is markedly **superlinear**: a 50× cardinality increase (20 → 1,000) produced a ~427× latency increase; a further 3.707× cardinality increase (1,000 → 3,707) produced a ~13.8× latency increase — closely matching **quadratic** scaling (3.707² ≈ 13.74). **Root cause identified by direct code inspection, not merely inferred from the curve shape:** `packages/graph-model/src/reconciliation.ts`'s `standingFilteredObservations` re-scans a subject's **entire accumulated observation history** (`subjectState.observations.filter(...)`) once per distinct-`observedAt` reconciliation step; because this M5 workload has one step per poll (3,707 distinct `observedAt` values, never batched), total reconciliation work is the sum `1 + 2 + ... + n ≈ n²/2` — an O(n²) cost in the number of corroborating observations for one subject, not the O(n) the freshness-dereference loop alone would suggest. This is a real, previously unmeasured characteristic of the accepted `m1-v1` reconciliation engine under sustained single-subject corroboration, not a defect introduced by the M5 connector itself.

### 23.4 Memory Result

RSS (`process.memoryUsage().rss`) was sampled before store construction, after `appendEvidence`, and after the 30 timed reads, at each cardinality, **within one long-lived measurement process** (all three cardinalities ran sequentially in the same Node process for measurement convenience). **Limitation, disclosed rather than smoothed over:** because RSS is a monotonic OS-level figure that does not reliably shrink after garbage collection, the _baseline_ RSS reported for the 1,000 and 3,707 cardinalities is inflated by retained memory from the earlier cardinalities measured in the same process — those baseline figures are **not** clean per-cardinality readings and must not be read as "the memory cost of holding exactly N Evidence records" in isolation. The **within-cardinality** delta (after-reads minus after-append, measured entirely within that cardinality's own timed-read loop) is directly meaningful: **+51,712 KiB** at n=20, **+443,216 KiB** at n=1,000, **+782,432 KiB** at n=3,707 — consistent with each read allocating temporary, uncollected garbage (arrays, snapshot structures) roughly in proportion to the same superlinear pattern the latency figures show, but this document does not claim a precise per-record byte cost from this data. A clean, isolated-process-per-cardinality memory measurement was not performed, consistent with keeping this reassessment the smallest measurement sufficient to resolve the open ADR-0018 question — the latency result alone already does that unambiguously (§ 23.5).

### 23.8 Implementation-Feasibility Precision Clarification (2026-08-21)

A subsequent implementation-feasibility reconnaissance examined whether [ADR-0038](../adr/0038-m5-reconciliation-scaling-remedy.md)'s remedy is mathematically achievable as originally worded. The benchmark numbers above (§§ 23.3-23.4) are unchanged and are not affected by this clarification; only the interpretation of what a remedy must achieve is refined:

- **Output-size lower bound.** The complete accepted revision history at this cardinality contains n revisions with provenance cardinalities 1, 2, 3, ..., n; complete materialization of that output therefore inherently contains n(n+1)/2 provenance-reference occurrences. At n = 3,707: **6,872,778 provenance-reference occurrences** — an inherent Θ(n²) output-size floor for any request that literally materializes the complete accepted revision history, not an implementation defect.
- **The actual measured defect.** Direct trace of the exact call path this benchmark exercised (`TopologyGraphStore.getSubject` → `SnapshotResolver` → `constructSnapshot` → `reconcileEvidenceAtHorizon`) found that an ordinary `"latest"`/current-state read reconstructs, canonicalizes, and SHA-256-hashes **all 3,707** historical revisions and only afterward discards **3,706** of them to return the one currently-valid revision. The 9.27-second median measured above is the cost of that full, repeated reconstruction — not an inherent cost of the one revision an ordinary current-state read actually needs.
- **What remains an accepted, expected cost.** The Θ(n²) complete-history materialization cost is correct and expected when a caller genuinely requests complete historical replay; it is not itself a defect and is not required to become sub-quadratic.
- **What ADR-0038's remedy therefore targets.** Following this clarification, ADR-0038 targets incremental per-observation derivation and interactive current-state read latency — not an impossible sub-quadratic requirement on complete-history materialization itself. See [ADR-0038](../adr/0038-m5-reconciliation-scaling-remedy.md)'s "Complexity Boundary" and "Current-State Read Defect" sections for the complete, precise statement.

### 23.9 ADR-0038-A Implementation and Measurement (2026-08-23, uncommitted candidate)

**Status: implemented on branch `perf/adr-0038-current-read`, not yet committed or merged.** This section records the factual result of ADR-0038-A — the first bounded implementation checkpoint, targeting Complexity Boundary (B) only (interactive current-state reads), explicitly not Boundary (A) (incremental derivation).

**Implementation boundary.** `packages/graph-model/src/snapshot-construction.ts`'s `constructSnapshot` was split into two pure, still cache-free functions: the existing reconciliation call, and a new package-internal export, `composeSnapshotFromReconciliationResult(reconciliationResult, resolvedIdentity)`, extracted unchanged from the post-reconciliation half of the prior `constructSnapshot` body. `packages/graph-model/src/snapshot-resolver.ts` (`SnapshotResolver`, the one stateful/caching layer this package already had per ADR-0023) gained a single-slot cache — `mostRecentReconciliationResult: {cacheKey, result} | undefined` — keyed by `(horizon, derivationVersion)` only, never `asOf`, never wall-clock time. A cache hit skips both the `EvidenceStore.listEvidence` load and the `reconcileEvidenceAtHorizon` call entirely and composes a fresh `Snapshot` directly from the reused `ReconciliationResult`. `buildSnapshot`/`buildSnapshotFromHorizonSelectedEvidence` (the two existing, exported entry points) are behaviorally unchanged — same signature, same per-call reconciliation, same documented purity.

**Why historical semantics remain unchanged.** Reconciliation is a pure function of `(evidenceRecords, horizon, policy)` alone (`reconcileEvidenceAtHorizon` takes no `asOf`); Evidence is append-only and a horizon's watermark never changes retroactively — the same invariant the pre-existing, unmodified `snapshotBuildsByIdentity` cache already relied on. A cached `ReconciliationResult` is therefore byte-identical to what a fresh recomputation at that same horizon would produce; the cache changes only _whether_ that computation is redone, never _what_ it computes. Every existing contractual invariant (content-addressed identifiers, provenance membership/ordering, confidence, `ruleTrace`, conflict/ambiguity, `validFrom`/`validTo`, revision count/sequence) is unaffected: 371 of the 372 pre-existing `packages/graph-model` tests required no change at all and pass exactly as before; the one remaining pre-existing test was deliberately corrected (§ "Tests added" below explains exactly why, not weakened) because its own assertion encoded an implementation detail this change intentionally altered. New differential coverage additionally proves a cache-hit `Snapshot` is `.toEqual()` a fresh, independently-resolved one at the same horizon.

**A real memory-safety finding, caught and fixed before checkpointing.** The first working version cached one `ReconciliationResult` per distinct `(horizon, derivationVersion)` ever seen, in an unbounded map. Because a `ReconciliationResult`'s own size grows with the square of its horizon (Complexity Boundary (C)), a performance run simulating the real M5 workload's continuous-polling pattern (one new horizon per read, 35 distinct horizons at n≈3,707) accumulated many such entries simultaneously and **exhausted the Node heap (`FATAL ERROR: ... JavaScript heap out of memory`)** — worse than the pre-ADR-0038-A baseline, not better. That unbounded-map design was rejected outright, before any checkpoint, and replaced with the single most-recent-entry cache this candidate submits. Re-running the identical COLD measurement (35 sequential, ever-advancing horizons at n≈3,707) against the corrected, single-slot design completed without the failure recurring, and all 376 tests (372 existing + 4 new) passed. **This narrowly confirms the single-slot design survived the one COLD run actually measured — it does not by itself prove every possible long-duration or higher-cardinality memory behavior is safe.** In particular, the single slot still holds exactly one `ReconciliationResult` whose own size scales with the square of the _current_ horizon (Complexity Boundary (C)); at a horizon far larger than the 3,707 measured here, even that one retained entry could itself become a meaningful memory consumer — a question this checkpoint did not measure and does not claim to have answered.

**Tests added/changed:** `packages/graph-model/src/snapshot-resolver.test.ts` gained **four new tests**: (1) no re-fetch/re-reconcile on an unchanged horizon; (2) newly appended Evidence is reflected on the very next read, never served stale; (3) a cache hit's output is identical (`.toEqual()`) to a fresh, independently-computed resolution at the same horizon; (4) a companion test proving a genuinely different horizon still triggers a fresh fetch and reconciliation. **One pre-existing test was edited, not left unchanged**: `"does not cache a referential-integrity failure — retrying the same identity re-attempts the build"` previously asserted that retrying the same failing identity increased `listEvidenceCalls()`; that assertion is no longer accurate given this change (reconciliation for that horizon is now legitimately reused), so it was corrected to assert the actual contractual property — the failure is still freshly re-evaluated on every retry (`assertReferentialIntegrity` runs fresh every call; nothing about the failure itself is cached) — while explicitly asserting `listEvidenceCalls()` now stays flat, with a comment explaining why. 371 of the original 372 tests required no change; 1 was edited; 4 are newly added — 376 total.

**Performance measurement**, same methodology as § 23.2 (real `mapObservedPodToEvidence`-shaped synthetic Evidence, deterministic advancing injected `Clock`, 5 warm-up reads, 30 timed samples), against the real, modified `InMemoryTopologyGraphStore`/`SnapshotResolver`, split into two honest cases:

**WARM — repeated `"latest"` reads at an unchanged horizon (no new Evidence between reads):**

| Cardinality | Median (before → after)   | p95 (after) | Max (after) |
| ----------- | ------------------------- | ----------- | ----------- |
| 20          | 1.57 ms → **0.07 ms**     | 0.11 ms     | 0.11 ms     |
| 1,000       | 670.13 ms → **1.89 ms**   | 2.26 ms     | 2.39 ms     |
| 3,707       | 9,273.59 ms → **7.19 ms** | 7.88 ms     | 7.91 ms     |

At n = 3,707, the WARM case is a **~1,290× improvement**, and the curve is now flat (effectively independent of historical revision count) rather than superlinear — direct proof a repeated `"latest"` read no longer reconstructs the complete historical revision sequence.

**COLD — one new Evidence record appended immediately before each timed read (a brand-new horizon every time, matching a read that lands right after a live poll):**

| ----------- | ----------- | ----------- | ----------- |
| 20          | 1.75 ms     | 2.69 ms     | 3.64 ms     |

**Scaling result.** WARM scales flat (sub-millisecond to single-digit-millisecond regardless of n, once the horizon has been reconciled once); COLD scales exactly as § 23.3's original superlinear curve, unchanged.

**Semantic-equivalence result.** All 376 `packages/graph-model` tests pass, including the four new ADR-0038-A tests and the one deliberately corrected pre-existing test (§ "Tests added/changed" above); the complete existing scenario suite (conflict, ambiguity, relationship chains, withdrawn support) required no change and is unaffected — none of that logic was touched.

**Does Complexity Boundary (A) remain necessary?** **Yes.** The real M5 workload polls continuously (every 2 seconds), so most individual current-state reads under realistic, spaced-out access (a human or dashboard checking state less often than the poll interval) will land on a horizon that has never been cached — the COLD case above — and will still pay close to the full original cost. The WARM improvement is real and valuable (bursts of near-simultaneous reads, retries, or multiple consumers reading the same resolved identity all benefit fully), but it does not, by itself, resolve the interactive-latency problem for the dominant realistic access pattern. **This is classified as RESULT B**, not RESULT A: current-state reads materially improve but remain meaningfully affected by the append/reconciliation architecture, and a second, separately authorized implementation checkpoint targeting Complexity Boundary (A) is recommended before M5 can close on this dimension.

### 23.10 ADR-0038-B Implementation and Measurement (2026-08-23, uncommitted candidate)

**Status: implemented on branch `perf/adr-0038-incremental-reconciliation`, not yet committed or merged.** This section records the factual result of ADR-0038-B — the second bounded ADR-0038 implementation checkpoint, targeting Complexity Boundary (A) (guarded incremental reconciliation for the safe monotonic new-horizon path). Boundary (B) (§ 23.9) remains unchanged and untouched by this work.

**Implementation architecture.** A new, dedicated unit, `packages/graph-model/src/incremental-reconciliation.ts` (Candidate C from the prior reconnaissance), implements a narrow, safety-first fast path entirely outside the accepted, pure `reconcileEvidenceAtHorizon` reference implementation, which remains completely unmodified in behavior and is this module's correctness fallback and differential-test oracle for every case the fast path does not confidently handle. Three small, already-existing internal helper functions in `reconciliation.ts` (`computeConfidence`, `deriveCanonicalClaim`, and a new extraction, `deriveSubjectIdentity`) were exported, unchanged in behavior, so the fast path reuses the reference's own logic rather than duplicating it — proven behavior-preserving by the complete pre-existing test suite passing unchanged before any new logic was added. `SnapshotResolver` (`snapshot-resolver.ts`) now holds a single `IncrementalReconciliationState | undefined` slot (replacing Boundary A's bare `ReconciliationResult` slot with a strict superset carrying the same single-slot memory guarantee) and, only on the `"latest"` path, either reuses an exact `(horizon, derivationVersion)` match (Boundary B, unchanged), advances the cached state via `advanceOrFallback` when the requested horizon is strictly ahead, or performs a complete one-off fallback. Pinned/cursor-bound requests never drive or persist incremental advancement, preserving their pre-ADR-0038-B behavior exactly, per the accepted design boundary.

**Fast-path safety precondition.** The fast path applies to one new atomic step's records for one subject only when: (1) the step's `observedAt` is strictly after the subject's own currently tracked open revision's `validFrom` (or the subject is genuinely new); (2) the touched subject's normalized key is not named by any `m1-v1` policy alias entry (today: exactly one, `ledger-api`/`ledger`); (3) every record in the step asserts the identical canonical claim as the subject's one existing open, uncontested, unambiguous revision (or each other, for a brand-new subject); and (4) — a real finding discovered only by implementing and differentially testing, not anticipated by the original reconnaissance — no currently open revision anywhere in the prior state carries a `"claim-supersession"` rule-trace marker. `reconcileEvidenceAtHorizon` recomputes every subject's state at every global atomic step (ADR-0022 § 7 step processing is not scoped per-subject), so a `"claim-supersession"` marker — valid for exactly the one step it was derived at — is dropped the very next time _any_ subject anywhere is evaluated at a new step, even with zero new Evidence for the marked subject itself. Any violation of any of these four conditions causes an immediate, complete fallback to `reconcileEvidenceAtHorizon` over the full horizon-selected Evidence; this module never returns a partially trusted incremental answer.

**Fallback and multiple-new-records handling.** New records between reads are grouped into ADR-0022 § 7 atomic equal-`observedAt` steps (via the existing, unmodified `sortEvidenceByTotalOrder`) and processed step by step; any step or record failing the safety precondition aborts the entire advance and falls back over the complete Evidence set. After any fallback, incremental state is rebuilt fresh from that fallback's own authoritative `ReconciliationResult` (tracking only subjects with exactly one open, uncontested, unambiguous, non-supersession-marked revision), so safe monotonic Evidence arriving afterward can resume the fast path without carrying forward any stale assumption.

**Differential-equivalence result.** A new test file, `incremental-reconciliation.test.ts`, drives `advanceOrFallback` and compares its result against a fresh `reconcileEvidenceAtHorizon` call at every horizon, covering: (A) single-source corroboration, the real M5 polling shape; (B/C/D/F) the complete real `demo-company` fixture catalog (multiple sources, conflicts, `m1-v1` alias ambiguity, and relationship revision chains) replayed one record at a time across all 20 horizons, and again with multiple horizons skipped between reads; (E) a source changing its own claim, including the `"claim-supersession"` one-step-only marker finding; a dedicated, focused regression test proving that marker's exact cross-subject shape directly (subject A's still-open, supersession-marked revision correctly forces a fallback for **unrelated** subject B's new Evidence, and A's own revision history — including the closed record's permanently-accurate marker and the newly reopened record's correctly-absent one — still matches the reference exactly); (H) deliberately late/out-of-order `observedAt`; (I) the existing late-old horizon-safety fixture shape, driven incrementally; and (J) a forced fallback (conflict, then conflict-resolution) followed by safe monotonic Evidence correctly resuming the fast path. All 10 tests pass; two genuine bugs (a subject that exists but is not fast-path-tracked being wrongly treated as brand-new, and the `"claim-supersession"` one-step-only marker) were found and fixed by this harness before it passed — not merely written to confirm an assumption. The cross-subject marker shape was previously exercised only indirectly through the fixture-catalog replay (scenario B/C/D/F's horizon 14); the focused test now names and proves it directly, with no further production change required — the existing global precondition already handled it correctly.

**Test counts.** `packages/graph-model`: **386/386** (376 after Boundary B, +10 new: the original 9 differential tests plus the one focused cross-subject `claim-supersession` regression test; every pre-existing test's own behavior is unchanged).

**Performance measurement**, same methodology as §§ 23.2/23.9 (real `mapObservedPodToEvidence`-shaped synthetic Evidence, deterministic advancing injected `Clock`, 5 warm-up reads, 30 timed samples), against the real, modified `InMemoryTopologyGraphStore`/`SnapshotResolver`:

**COLD — the Boundary (A) target workload (one new Evidence record appended immediately before each timed read):**

| Cardinality | Before (§ 23.9) median | After median | After p95 | After max |
| ----------- | ---------------------- | ------------ | --------- | --------- |
| 20          | 1.75 ms                | **0.29 ms**  | 0.57 ms   | 0.68 ms   |
| 1,000       | 460.92 ms              | **5.65 ms**  | 6.89 ms   | 6.98 ms   |
| 3,707       | 6,291.56 ms            | **26.18 ms** | 28.14 ms  | 28.77 ms  |

At n = 3,707, this is a **~240× improvement** over the Boundary-B-only COLD baseline, and a **~354× improvement** over the original, pre-Boundary-B-and-A § 23.3 baseline (9,273.59 ms). 26.18 ms sits just under this project's own established sub-30 ms "comfortably interactive" bar (M2-F/M4-E § 20.6).
